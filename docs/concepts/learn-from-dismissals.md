# 🎓 Learn from dismissals

A dismissal only ever applied to its own change, after the review had run, and the model never saw it. So a false positive that people rejected last week came back on the next change, and someone had to read it and dismiss it again. Now a review is told what people rejected in the repository, and why.

**What a review is told.** For each skill it runs, a review gets a list of earlier dismissals of that skill: the file, the title, the severity and the reason. Nothing else: not who dismissed it, and not on which change. The list goes to the batch runs and the cross-batch run (all of it) and to the verification run (the blocking entries only). The model is told to treat it as data, to leave out a finding that is the same mistake, to raise it anyway if this code really has the problem, and never to let a rejected suggestion excuse a blocking finding.

**Who teaches.** A dismissal teaches when the person had write access or better when they made it, and gave a reason. A change's author with read access only, for example a contributor from a fork, can still dismiss a suggestion on their own change, as before, but it teaches nothing. A blocking dismissal is left out of a review of a change by the person who made it, so nobody clears their own blocker by rejecting it on another change first. When the change's author is unknown, every blocking dismissal with a known dismisser is left out. A dismissal from before the upgrade, or one made in the dashboard (an account has no platform identity), has no recorded dismisser, so this rule can't apply to it; those from before the upgrade fade within 90 days, and a blocking dismissal from the dashboard teaches all the same.

**Limits.**

- The same skill only. A reason given to the security skill never quiets another.
- The last 90 days, and 20 entries a skill: blocking ones first, then the newest. One entry per finding, wherever it was dismissed.
- Dismissals from any change of the repository count, open, merged or closed.
- Editing a skill keeps its dismissals. Renaming it starts fresh.
- A list too large for the Job is dropped first, before an incremental review is turned into a full one.

**Past dismissals.** The repository's **Past dismissals** tab, for its maintainers and admins, shows what teaches its reviews right now: one row for each finding, with the skill, severity, file, title, reason, who dismissed it, when, and a link to the change. It follows the rules above except the limit of 20 entries a skill and the rule about a change's own author, so it can show more than a review is told. **Stop using** on a row stops every dismissal of that finding in the repository from teaching, so the next one with the same fingerprint doesn't take its place. The dismissals stay on their changes, no review is decided again and nothing happens on the platform, whatever state the change is in. It works on a repository managed by config too, and is recorded in the [audit log](dashboard.md#audit-log) as `dismissal_stopped`. A mistaken stop can't be undone from the list; a new dismissal of the finding teaches again. **Restore** on the review page is a different thing: it takes a dismissal off its change. Anyone with write access who dismisses that finding again with a reason, on any change, starts the lesson again, and their dismissal replaces one that didn't teach, such as a read-only author's on the same change.

**The model decides.** No code removes a finding because of a dismissal: a finding from another change with the same fingerprint is not set aside by pergent.sh. The model is asked to leave out the same mistake, so a repeat can still slip through, and a wrong dismissal keeps misleading reviews until it ages out or someone stops it. A skill that left a finding out says so, and the comment shows a note such as `Left out because of past dismissals: Token compared with == (Token compared with == in api/auth.go)`. A blocker left out this way can give a clean review and an approval, as verification dropping a finding can today; the note shows what happened.

**Turning it off.** The switch is **Learn from dismissals** in a repository's Settings, the default under **Admin → Settings**, or `repositories[].learn_from_dismissals` in the config ([Config reference](../reference/configuration.md)). With it off, reviews are not told anything. Pergent v0.5.0 or later reads the list; an older image in `jobs.image` ignores it.
