# 🌐 HTTP routes

[`openapi.yaml`](../../openapi.yaml) at the root of the repository describes every route below as an OpenAPI 3.1 document: the parameters, bodies, status codes, who may call each route and the JSON of each answer. Use it to read the API or to generate a client. It also describes the result a review Job posts to `POST /runs/{id}/result` (pergent's result schema v1), as pergent is a CLI with no HTTP API of its own. The embedded dashboard pages are not in it. pergent.sh is 0.x, so the API may change between minor versions. It also describes the callback pergent.sh sends to an API client when a review ends, as the webhook `reviewFinished` (a request pergent.sh makes, not a route it serves: [Get the result by callback](../setup/review-api.md#get-the-result-by-callback)). A test, `internal/dashboard/openapi_test.go`, fails when the file and the code disagree about the routes, who may call them, or the JSON fields of the answers. It needs no database: run it with `go test -run TestOpenAPI ./internal/dashboard/`.

| Route | Used by |
| --- | --- |
| `POST /webhooks/gitlab/{instance}` | GitLab merge request (`Merge Request Hook`) and note (`Note Hook`) webhooks; any other event is answered 200 and ignored. The `X-Gitlab-Token` header is compared in constant time with the instance's secret; a mismatch gets 401 and is otherwise ignored. An authenticated webhook whose payload can't be used (not JSON, no project id or merge request iid, a malformed head SHA) gets 200 and a warning in the log, because GitLab counts failed deliveries toward disabling the hook. |
| `POST /webhooks/github/{instance}` | The GitHub review App's `pull_request` and `issue_comment` webhooks (the second carries [commands](../concepts/commands.md)); any other event is answered 200 and ignored. `X-Hub-Signature-256` (HMAC-SHA256 of the body with the instance's webhook secret) is compared in constant time; a missing or wrong signature gets 401 and is otherwise ignored. A repository that isn't in the config gets 200 and is ignored. |
| `POST /runs/{id}/result` | A review Job delivering its result, with its one-time bearer token. |
| `POST /skill-fetches/{id}/result` | A skill fetch Job delivering the skills it read from a public URL, with its one-time bearer token (only with the dashboard on). A wrong token gets 401, a second result or one after the fetch gave up 409, a body over 4 MiB 413. |
| `POST /readiness-scans/{id}/result` | A readiness scan Job delivering what it found in a repository, with its one-time bearer token (only with the dashboard on). A wrong token gets 401, a second result or one after the scan ended 409, a body over 1 MiB 413. |
| `GET /v1/client` | The [review API](../setup/review-api.md): the client a key belongs to, its limits and its `usage` this UTC month (`month`, `tokens_used`, `tokens_left`). `Authorization: Bearer <key>`, a client key an admin made. A missing, unknown, revoked or expired key gets 401 `unauthorized` with one body for all; any other path under `/v1/` gets 404 `not_found` with a key. A key past its client's requests per hour (a bucket refilled evenly) gets 429 `rate_limited` with `Retry-After` on every `/v1/` route. Errors are `{"code", "message"}` and every answer is `Cache-Control: no-store`. Only with `dashboard.url` set. |
| `POST /v1/reviews`, `GET /v1/reviews/{id}` | The [review API](../setup/review-api.md): ask for a review of a change, and read it. Same key and error format as `GET /v1/client`. `POST` takes `{"subject", "tenant", "title", "description", "files": [{"path", "old", "new"}]}` and an optional `Idempotency-Key` header; it answers 202 with the review and a `Location` header (the same key and body returns the first review), 413 `too_large` (bytes, files, or too large once packed), 422 `invalid` (also a body that could not be read) or `idempotency_key_reused`, 429 `budget_used_up` (with `Retry-After`), or 409 `cannot_review`. `GET` answers 200, or 404 `not_found` for another client's review, an unknown ID and a malformed one alike. Only with `dashboard.url` set. |
| `POST` and `DELETE /v1/reviews/{id}/findings/{finding}/dismiss` | The [review API](../setup/review-api.md): dismiss a finding of a completed review for its subject, or take it back. `POST` takes `{"reason"}` (1 to 500 characters, no control character but a line break or a tab, in a body of at most 16384 bytes). Both answer 200 `{"status"}` (`dismissed`, `already_dismissed`, `restored`, `not_dismissed`), 404 `not_found` (as for `GET`, or no such finding), 409 `not_finished` or, for `POST` only, 413 `too_large` (body over 16384 bytes) and 422 `invalid` (not JSON or UTF-8 text, or a reason that is empty, too long or holds a control character). Only with `dashboard.url` set. |
| `GET /metrics` | Prometheus, on the `metrics_listen` port only; the main port never serves it ([Metrics](../concepts/metrics.md)). No sign-in: scrape it inside the cluster, never through `public_url`. |
| `GET /healthz` | Health check. It answers as soon as the server starts: pergent.sh serves right away and runs the startup reconcile in the background. |
| `GET /auth/oidc/login`, `GET /auth/oidc/callback`, `POST /auth/logout` | [Dashboard](../concepts/dashboard.md) sign-in with OIDC ([Sign-in](../concepts/dashboard.md#sign-in)), and sign-out. The callback sends every refusal to `/sign-in?error=<code>`. Only with `dashboard.url` set. |
| `GET /auth/csrf`, `POST /auth/password`, `POST /auth/password/change` | Password sign-in. `GET /auth/csrf` hands out the sign-in form's CSRF token (a cookie and `{"csrfToken": ...}`); `POST /auth/password` takes `{"username", "password"}` with that token in `X-CSRF-Token` and answers 204 and the session cookie; `POST /auth/password/change` takes `{"current", "new"}` for a signed-in password account. See [Password sign-in limits](../concepts/dashboard.md#password-sign-in-limits). Only with `dashboard.url` set. |
| `/api/...` | The dashboard's JSON API. Every route but `GET /api/sign-in-options` needs a session; the admin routes answer a user `404`, like an unknown path; writes need the `X-CSRF-Token` header. Only with `dashboard.url` set. The review page's buttons use `POST /api/reviews/{instance}/{project}/{number}/rerun` (`{"failed": true or false}`; 202 with `queued`, `already queued`, `nothing failed` or `whole review`; 409 `the monthly token quota is used up` when the quota is used up, unless the caller is an admin; 429 at a re-run cap), `.../start` (`{"head"}`, for a change whose review waits for someone to start it; 202 with `queued` or `already queued`; 409 for a quota that is used up, unless the caller is an admin, and for a change that is closed, a draft that is not reviewed, or a head pushed since the page was loaded; 429 at the change's re-run cap), `.../dismiss` (`{"fingerprint", "reason"}`; 200 with `dismissed` or `already dismissed`; a reason of up to 500 characters; 400 `the reason is too long` above) and `.../restore` (`{"fingerprint"}`; 200 with `restored` or `not dismissed`), for maintainers and admins of the repository, config repositories included. The Readiness tab uses `GET /api/repositories/{instance}/{project}/readiness` (anyone who can see the repository) and `POST .../readiness/scan` (maintainers and admins; 202 with the queued scan, 409 while one is queued or running, 429 within 5 minutes of the latest scan, 404 for a repository that isn't switched on or when scans are off). |
| `GET /api/runs/{id}/log` and `GET /api/runs/{id}/diagnostics` | What was kept of a review's Job: the pergent log, and the clone log with, for admins of the repository, the pod's state. Anyone who can see the run reads the clone log, with linked repositories masked (it may be empty) and no `podState`. `404` for a run that doesn't exist or that kept nothing. See [Troubleshooting a failed review](../setup/troubleshooting.md). |
| `GET /api/admin/usage`, `GET /api/admin/usage.csv`, `GET /api/repositories/{instance}/{project}/usage` and `GET /api/repositories/{instance}/{project}/skill-results/tokens` | The [Usage](../concepts/usage.md) page and a repository's usage page, the CSV export, and the Skill results tab's cost section ([Skill results](../concepts/skill-results.md)). Admins only: anyone else gets `404`. `days` is 1 to 90 (30 by default), and 30 or 90 for the tokens route. The repository routes need a repository that is switched on. |
| `GET` and `POST /api/admin/models`, `PUT` and `DELETE /api/admin/models/{id}`, `POST /api/admin/models/{id}/default` | The list of [models](../concepts/models.md): list, add, change the base URL or key, remove, set the default. Admins only. They replace `GET` and `PUT /api/admin/llm`. A repository's model is the `model` key of its settings (`PUT /api/repositories/{instance}/{project}/settings`), changed by admins only. |
| `PUT /api/admin/instances/{name}/token-quota` | Sets an instance's [monthly token quota](../concepts/token-quota.md): `{"monthlyTokenQuota": n}`, a whole number from 1 to 1000000000000000, or `null` for none. 204; 400 for a bad number, 409 for an instance in the config (its quota is in the config file) or one being removed. Admins only. A repository's quota is the `monthlyTokenQuota` key of `PUT /api/repositories/{instance}/{project}/settings`. |
| `GET` and `PUT /api/admin/comment-footer` | The [footer text](../concepts/comment-layout.md#the-footer-text) of review comments. `PUT` takes `{"note": "..."}`; an empty note goes back to the default. Admins only. |
| `GET` and `POST /api/admin/api-clients`, `GET`, `PUT` and `DELETE /api/admin/api-clients/{name}` | The clients of the [review API](../setup/review-api.md): list (name, key count and, from the 1st of the UTC month, its reviews, how many failed and the tokens they used), add, read with its keys, change its skills, model, callback URL and limits (the name never changes), remove. `POST` takes `{"name", "skills", "modelId", "callbackUrl", "limits"}` (`limits` left out means the defaults) and answers 201 with the client and its `callbackSecret`, shown once; 409 when the name is taken. `PUT` needs `limits` and answers 200 with the client. `DELETE` answers 204, ends the client's keys at once and deletes the Jobs of its running reviews (a queued review has no Job; its data goes with the client). 400 for a bad value, 404 for a client that isn't there. Admins only. |
| `GET /api/admin/api-clients/{name}/reviews`, `GET /api/admin/api-reviews/{id}`, `GET /api/admin/api-reviews/{id}/log` and `GET /api/admin/api-reviews/{id}/diagnostics` | A client's [API reviews](../setup/review-api.md), newest first, 50 a page, and one review. The list takes `tenant`, `subject`, `status` (`queued`, `running`, `completed`, `failed` or `superseded`; 400 for any other) and `cursor` (the last answer's `nextCursor`), and answers `{"items", "nextCursor"}`. A review's page holds its client, key name and model, a `failure` (`step`, `reason` and the admin-only `detail`) and `review`, the body `GET /v1/reviews/{id}` answers with: the one stored when it was published, else the one built from its state. The log and diagnostics are those of a merge request's run page, with the clone log whole and the pod's state. 404 for an unknown ID and for a merge request's run. Admins only. |
| `POST` and `DELETE /api/admin/api-reviews/{id}/findings/{finding}/dismiss` | The same for an admin, on any client's review: `POST` takes `{"reason"}`, both answer `{"status"}`. 400 for a bad reason, 409 for a review not completed, 404 for an unknown review or finding. The review's page then lists `history` (each dismissal and restore, with the actor) and `dismissals` (what is dismissed now for its subject). Not audited. Admins only. |
| `POST /api/admin/api-clients/{name}/secret`, `POST /api/admin/api-clients/{name}/keys` and `DELETE /api/admin/api-clients/{name}/keys/{id}` | Rotate the callback secret (200 with the new `callbackSecret`, shown once; the old one keeps signing for 24 hours), make a key (`{"name", "expiresAt"}`; 201 with the key's row and its `secret`, shown once; 409 when the client has a key of that name) and revoke a key (204). Admins only. |
| `GET /` and every other path | The dashboard's pages: `/sign-in`, `/admin/sign-in`, `/signed-out`, the user pages and the admin pages under `/admin` ([Two areas](../concepts/dashboard.md#two-areas)). Only with `dashboard.url` set; without it they are 404. With JWT sign-in, a `GET` of a page by someone with no session and a valid token starts a session ([Sign-in](../concepts/dashboard.md#sign-in)); `/signed-out` never does. |

Logs are JSON on stdout. Secrets are never logged.
