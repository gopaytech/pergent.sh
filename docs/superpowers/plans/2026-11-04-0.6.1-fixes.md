# pergent.sh 0.6.1 fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Four fixes found while running 0.5.4–0.6.0: a Job timeout that fits 40 steps, a Timeout field that never silently resets, Admin defaults that keep following the config, and a visible note when the review App can't read classic branch protection.

**Architecture:** Each fix is local:
- a config default and a startup warning;
- two web form fields;
- a richer Admin defaults view (the config's own values, and which defaults are pinned) with the web form sending `null` for a value equal to the config's;
- one per-project flag recorded at reconcile and shown on the Integrations page.

**Tech Stack:** Go, Postgres migrations (`internal/store/migrations`), React/TypeScript (`web/`).

**Spec:** none written; the owner approved this description in chat on 2026-11-04:
1. The default `jobs.timeout` goes from 10 to 30 minutes, and a startup warning appears when a timeout allows less than 30 seconds a step.
2. The Timeout field becomes a text field with a visible error instead of silently resetting.
3. Admin defaults show "from config: X", store "not set" for a value equal to the config's, and offer **Use config value** on a pinned field.
4. Integrations shows when the review App lacks Administration: Read, in which case a classic "require conversation resolution" rule is treated as off. This is not a "Needs attention" item.

## Global Constraints

- Public repository: no employer names, internal hostnames or real people in code, docs, tests or commits.
- Approval logic, review behaviour and inline threads don't change.
- Migration `0018` adds only a column with a default, so 0.6.0 keeps running on a migrated database.
- Exact strings are copied verbatim from this plan.
- Match the surrounding code (comment density, naming, error wrapping, table-driven tests where the package uses them).
- DB tests skip without `PERGENT_SH_TEST_DATABASE_URL`, and there is no local Postgres. They must compile; CI runs them.
- Stage files by path; `.superpowers/` is not gitignored.

## Review Focus

1. **An existing install whose Admin defaults were saved before 0.6.1** has `job_timeout_seconds = 600` stored, so it keeps 10 minutes after the upgrade. The page must show that value as pinned next to "from config: 1800 s" with **Use config value**, and the upgrade note must say to click it. Task 3 test `TestDefaultsViewConfigAndPinned`.
2. **Saving Admin defaults without touching a field** must not pin it. Task 3 web test "saving untouched defaults sends null for values equal to the config".
3. **A Timeout typed as "abc", "", "59" or "7201"** must show the error and send nothing. It must never send `null`, which would reset silently. Task 2 tests.

**Interfaces:**
- `DefaultsView` keeps its flat fields (the effective defaults, as today) and gains:
  ```go
  // Config holds the values the config gives (jobs.* and the built-in
  // defaults), before anything saved here. Skills has no config value.
  Config DefaultValues `json:"config"`
  // Pinned says which defaults were saved here and so no longer follow the
  // config, by JSON key (approve, reviewDrafts, inlineFindings,
  // failureStatus, jobTimeoutSeconds, maxTurns, jobMemory,
  ```

  `DefaultValues` holds the same fields as `DefaultsView` minus `Skills`, with the same JSON keys. `Config` comes from the resolver's config-only defaults (`Defaults("", "")`, or the equivalent that ignores `repo_defaults`; check what the dashboard's `Repos` interface offers and add a method if needed). `Pinned[k]` is true when the stored `RepoDefaults` field for `k` is non-nil.

- On save, each of the nine fields whose value equals its `config` value is sent as `null`. Every other value is sent as today. Skills are unchanged.

Migration `0018_protection_readable.sql` (exact):
```sql
-- Whether the review App may read a GitHub repository's classic branch
-- protection (Administration: Read). Without it, a classic "require
-- conversation resolution" rule is treated as off and suggestion threads may
-- block a merge. Always true on GitLab.
ALTER TABLE projects ADD COLUMN protection_readable boolean NOT NULL DEFAULT true;
```

Behaviour:
- Reconcile sets `p.ProtectionReadable` from the installation's permissions:
  - true when the permissions are unknown (nil), or `administration` is `read` or `write`;
  - false otherwise;
  - a failed read keeps the stored value, and a new project gets true.
- `UpsertProject` (GitLab) always stores true.
- The Integrations page: for a GitHub repository with `inlineAvailable` true and `protectionReadable` false, show (exact): `Can't read classic branch protection (the review App lacks Administration: Read); a "require conversation resolution" rule there is treated as off.` It shows nothing when inline findings are off; that note already says enough.
- It is not a "Needs attention" item.
