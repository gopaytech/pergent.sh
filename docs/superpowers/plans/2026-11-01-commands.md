# MR/PR Commands Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People re-run a review, re-run only failed skills, and dismiss or restore findings from MR/PR comments and dashboard buttons, under platform- and team-based permissions, re-run caps, and with the review comment, status and approval re-decided without a new LLM run when only dismissals change.

**Architecture:** pergent's comment formatter becomes a public package `github.com/gopaytech/pergent/render` that both pergent's CLI and pergent.sh use. pergent.sh stores commands from webhooks (answered fast) and processes them in the engine loop; dismissals are stored per MR by fingerprint and severity and applied at publish time through `render.ApplyDismissals`; re-runs get their own store path (`EnqueueRerun`) with a trigger and an optional skill subset merged with the base run's kept skills.

**Tech Stack:** Go 1.24.8 (pergent.sh's `go` line rises to match pergent), pgx v5, React 18 + TS + TanStack Query 5 + Vitest.

**Spec:** `docs/superpowers/specs/2026-11-01-commands-design.md` (read with the dashboard and organization designs, whose constraints still hold).

## Global Constraints

- Public repositories (pergent.sh and pergent): example names only; private-name scan in pergent.sh prints nothing: `git grep -niE 'golabs|gojek|gopay[^t]|goto\b' -- . ':!go.sum' ':!docs/superpowers/plans/*' ':!web/package-lock.json'` (run the same pattern in pergent with `':!go.sum'`).
- Commands: `@<bot> review`, `@<bot> review failed`, `@<bot> dismiss <id> [reason]`, `@<bot> help`. `<bot>` = GitLab review bot username / GitHub review App slug. Only the first command of a comment runs; commands without the mention are ignored.
- Accepted comments: newly created, top-level, on an MR/PR; never edits, deletions, GitLab `DiffNote`/`DiscussionNote`, system notes; never by the review bot, the approve bot, or a login ending in `[bot]`.
- Re-run (comment): GitLab Developer (30) or above; GitHub `write`, `maintain` or `admin`. Re-run (button): repository role maintainer or admin.
- Dismiss blocking: never the MR/PR author on their own change; GitLab Maintainer (40) or above, GitHub `maintain` or `admin`, or (button) repository role maintainer/admin (operators included). Dismiss suggestion: anyone who may re-run. A reason is required to dismiss a blocking finding.
- Restore: dashboard button only, anyone who may re-run (author included).
- A dismissal is stored per MR/PR by fingerprint with the severity it was made at; it applies to a later report of that fingerprint only at the same or lower severity (blocking covers suggestion; suggestion never covers blocking).
- Dismiss/restore never start a run: they re-decide and re-publish the latest review. A review whose remaining blocking findings are all dismissed is approved under the existing rules (approval on, not draft, nothing failed).
- Re-deciding a head as not approved withdraws the bot's approval of that head and target.
- `review failed`: re-runs skills whose last verdict is `failed` or that policy counts as failed (`no_blocking_issues` with `files.not_reviewed`); keeps the other skills' results; with no per-skill results (error result, failure reason, or no published review of the current head) it does a full re-run and replies `the whole review failed, so all of it is re-run`; with nothing failed it replies `nothing failed` and does nothing.
- Abuse limits: a re-run for a head already queued or running is not queued twice; a comment command is accepted at most once per MR/PR per 30 seconds per command and finding ID (dropped ones get 👎); re-run caps count command and button re-runs only (pushes and opened MRs always run): default 10 per MR/PR and 50 per repository per UTC calendar day; set in dashboard defaults, per repository, and `repositories[].rerun_limit_per_mr` / `rerun_limit_per_repo` in the config; admins change them; at the cap reply `re-run limit reached for this <MR|PR>; it resets at 00:00 UTC` and queue nothing.
- Reactions: GitLab award emoji `eyes`, `thumbsup`, `thumbsdown`; GitHub reactions `eyes`, `+1`, `-1`. 👀 when picked up, 👍 when done, 👎 plus one reply when refused. A reply never says more than the commenter can see on the platform. A missed reaction never blocks the command.
- Audit actions: `review_rerun`, `review_rerun_failed`, `finding_dismissed`, `finding_restored`, recording actor (`username (platform instance)` for comment commands, the session's label for buttons), instance, project, MR number, head, fingerprint and reason in `detail` (never a secret).
- Webhook handlers verify, store and answer; platform calls for permissions, reactions and replies happen in the engine's command step, bounded per pass so reviews are never blocked.
- pergent's CLI output must be byte-identical to today's for every existing golden/test after the formatter moves.
- Verification per task (pergent.sh): `PERGENT_SH_TEST_DATABASE_URL='postgres://postgres:pergent@localhost:55432/pergent_test?sslmode=disable' go test -count=1 ./...` with no DB skips, `go vet ./...`, and for web changes `cd web && npm test -- --run && npm run lint && npx tsc --noEmit`. pergent: `make test`, `go vet ./...`.
- Commits: `git -c user.email=zufardhiyaulhaq@gmail.com commit`, conventional subjects, message ends `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push without the user's OK. Never run `go clean`, `docker build`, `docker builder prune` or cache/disk cleanup.
